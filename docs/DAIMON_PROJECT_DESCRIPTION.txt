DAIMON PROJECT DESCRIPTION
==========================

作成日: 2026-06-16
対象リポジトリ: hjosugi/daimon


1. このプロジェクトは何か
--------------------------

Daimon は、投稿SNSをそのまま作るプロジェクトではない。

中心にあるのは「POV (Point of View / 観点)」である。

通常のSNSでは、ユーザーは文章を投稿し、他人はそれに対していいねやコメントを行う。そこでは会話の単位は「投稿」になる。しかしDaimonが目指しているのは、投稿そのものよりも、その投稿や作品や体験をどの観点から見ているのかを明示し、その観点を通して人と人が接続できる場所である。

言い換えると、Daimon は「人が何を好きか」だけを見るのではなく、「なぜそれを好きだと思ったのか」「どの観点で評価しているのか」「同じ対象を見ているが違う観点を持つ人は誰か」を扱う。

単なる投稿SNSではなく、POVを通じて他人の感性構造に触れるためのプロトタイプである。


2. 解決しようとしている課題
----------------------------

2.1 通常のSNSは主観をそのまま流しすぎる

多くのSNSでは、投稿は時系列または人気順で流れる。ユーザーは「好き」「嫌い」「面白い」「微妙」などの反応をするが、その反応がどの観点に基づくものなのかは明示されない。

たとえば、ある作品について次のような意見があったとする。

- 最高だった
- 微妙だった
- シナリオは良いがテンポが悪い
- キャラクターは好きだが結末は納得できない
- 演出は弱いが世界観はかなり良い

通常のSNSでは、これらは単に賛否や温度差として処理されやすい。結果として、違う意見の人同士は衝突しやすく、同じ意見の人同士は閉じた同意圏に集まりやすい。

Daimon が扱いたいのは、その中間である。

完全に同じ意見ではないが、同じ観点を見ている人。
意見は違うが、論点は共有している人。
好き嫌いは違うが、評価軸が似ている人。

この接続は、通常のSNSの「いいね」や「フォロー」だけでは作りにくい。


2.2 コメントが投稿に閉じると、観点が蓄積されない

普通のコメントは「この投稿について話す」ためのものだ。

しかしDaimonで重要なのは、POVコメントである。

普通のコメント:
  この投稿について話す。

POVコメント:
  この観点で見るとどうかを話す。

この差が大きい。

投稿コメントは投稿が流れれば埋もれる。だがPOVコメントは、同じ観点を持つ別の投稿や別のユーザーへ接続できる。つまり、POVコメントは単なる返信ではなく、観点に対する知識や違和感や補足を蓄積する場所になる。


2.3 キーワード検索やベクトル検索だけでは「人間の評価軸」が拾えない

Daimon は embedding と Qdrant を使って、投稿本文の意味的な近さを検索できる。これは重要だが、それだけでは十分ではない。

なぜなら、人間の面白さは文章の意味的近さだけでは決まらないからである。

同じ文章でも、どの観点で評価しているかが違えば、全く別の意味を持つ。

たとえば「短い」という特徴は、ある人にとっては「テンポが良い」かもしれないし、別の人にとっては「描写が足りない」かもしれない。

vector は意味的な近さを見る。
POV は評価軸を見る。

Daimon はこの2つを組み合わせる必要がある。


2.4 レコメンドは「近いもの」だけ出すと閉じる

一般的な推薦は、ユーザーが好みそうな近いものを出す。これは便利だが、感性の探索には弱い。

Daimon が出したいのは、単に近い投稿だけではない。

- 自分と近い投稿
- 自分と遠いが同じPOVを持つ投稿
- 同じPOVだが反対の見方をしている投稿
- 自分が保存した投稿と似たPOVで新しい議論が起きている投稿
- 自分と違う人が、同じ観点をどう見ているかが分かる投稿

特に重要なのは、次の状態である。

  意見は違うが、見ている観点が同じ。

これは通常のSNSでは衝突になりやすい。しかしPOV空間では、良いコミュニケーションの入口になる。


3. Daimon の基本思想
--------------------

3.1 POVはタグではなく、会話の軸である

現時点の実装では、投稿に povs: string[] が付いている。これは入口としては正しい。しかし最終的に必要なのは、単なるタグではなく「この投稿がこのPOVにどう関係するか」という主張である。

タグ:
  この投稿には「シナリオがいい」というラベルが付いている。

POV主張:
  この投稿は「シナリオがいい」という観点に A で当てはまり、その理由は「伏線回収が自然だから」である。

この違いが、Daimonを普通のタグSNSから分ける。


3.2 POVは open な語彙である

POVは最初から完全な分類体系として管理しない。

ユーザーが自由に作り、使い、コメントし、後から統合・説明・類義語整理ができるようにする。

重要なのは、最初から細かい統計や管理画面を作り込むことではない。むしろ、POVが自然に増え、ユーザーが自分の言葉で観点を作れることが重要である。

ただし、将来的に似たPOVや重複POVを整理できるよう、POV定義テーブルは必要になる。


3.3 評価は一枚岩ではなく、観点ごとの主張として保存する

「この投稿が好き」「この作品が好き」ではなく、以下のように分解して保存する。

- どのPOVか
- どの対象に対するPOVか
- どの程度当てはまるか
- その理由は何か
- ネタバレを含むか
- どのユーザーが作った主張か

これにより、同じ投稿を見たユーザー同士が、全面的な賛否ではなく、観点ごとの会話をできるようになる。


3.4 Daimon は「感性のデータベース」である

Daimon は、単なるフィードではなく、ユーザーが作る感性のデータベースである。

保存されるべきものは、投稿本文だけではない。

- 投稿
- POV
- POVに対する主張
- POVに対するコメント
- POVへの共感、問い、違和感、補足
- ユーザーがどのPOVをよく使うか
- ユーザーがどのPOVに反応するか
- ユーザー同士がどのPOVで近いか、遠いか

これらが蓄積されることで、Daimonは「投稿を読む場所」から「他人の感性構造を読む場所」に変わる。

4.4 PostgreSQL

現在の主要テーブル:

    ユーザー情報。username, email, password_hash, avatar_url, bio を持つ。

  sessions
    ログインセッション。

  posts
    投稿本文。

  povs
    投稿に付いたPOV。現時点では post_id と pov の対応を持つ。

  likes

  follows
    ユーザー間フォロー。

  bookmarks
    保存済み投稿。ランキング上は強い興味シグナルとして扱う。

役割:
  投稿本文の embedding を保存し、近傍検索する。

payload:

  user_id
  tags
  created_at

考え方:
  PostgreSQLが正本。
  Qdrantは検索用の派生インデックス。
  壊れても再生成できる。


4.6 Redis

役割:
  任意の read-model cache。

現在:
  設定されていない場合は no-op として動く。
  precomputed feed などに使える。


4.7 backend/

場所:
  backend/

役割:

  Go API + ml-service + PostgreSQL + Qdrant + Redis

6. 現在まだ弱いところ
----------------------

6.1 POVがまだタグ寄りである

現時点では、povs テーブルは「投稿にこのPOVが付いている」という情報を持つ。

しかし本当に必要なのは、post_pov_assertions である。

これは「この投稿がこのPOVに対してどのように当てはまるか」という主張を保存するテーブルである。

必要なカラム例:

  id
  post_id
  pov
  grade
  comment
  spoiler
  confidence
  created_by
  created_at
  updated_at

grade:
  A: 強く当てはまる
  B: ある程度当てはまる
  C: 弱く当てはまる、または議論の余地あり

ここで重要なのは、grade は会話の stance ではなく、対象への当てはまりであること。

POVコメントの stance:
  support
  question
  oppose
  note

POV主張の grade:
  A
  B
  C

この2つは混ぜない。


6.2 POV自体の説明がまだない

現時点では、POVは文字列として存在している。

次に必要なのは pov_definitions である。

必要なカラム例:

  id
  title
  normalized_title
  category
  description
  examples
  synonyms
  parent_pov
  merged_into
  created_by
  created_at
  updated_at

ただし、最初から重い管理画面や詳細統計は不要である。

まずは、POVページで説明を編集できる程度でよい。


6.3 POVページがまだ入口段階である

現在のPOVページには、関連投稿とPOVコメントがある。

今後必要なのは、細かい統計ではなく、読むための整理である。

優先度が高いもの:

  このPOVが付いた投稿
  このPOVへの最近のコメント
  このPOVに対するA/B/C主張
  POVの説明
  似たPOV候補
  隣接するPOV候補

優先度が低いもの:

  詳細ランキング
  ユーザー偏差値
  複雑なグラフ可視化
  高度なクラスタリングUI


6.4 タイムラインにPOV活動がまだ十分混ざっていない

現在のタイムラインは、投稿本文のembedding、ユーザーcentroid、POV共有、保存、人気、recencyを使っている。

今後は、投稿そのものだけでなく、POV活動も混ぜるべきである。

例:

  最近「シナリオがいい」で議論されています。
  あなたが保存した投稿と同じPOVで、新しい意見があります。
  同じPOVで別の見方があります。
  あなたと遠い人が、同じPOVに反応しています。

これにより、タイムラインは単なる投稿一覧ではなく、感性空間の変化を表示する場所になる。


7. 次に入れるべき機能
----------------------

7.1 post_pov_assertions

最優先。

目的:
  投稿とPOVの関係を、単なるタグではなく主張として保存する。

最小仕様:

  grade: A/B/C
  comment: 一言理由
  spoiler: true/false
  confidence: 0.0 - 1.0
  created_by: user_id

UI:
  投稿作成時、POVごとにA/B/Cを選べる。
  任意で一言理由を書ける。
  ネタバレフラグを付けられる。

表示:
  投稿カード内で、POVごとに grade と一言を見せる。
  POVページでは、そのPOVに対する主張を一覧できる。


7.2 pov_definitions

目的:
  POVを説明可能にする。

最小仕様:

  title
  category
  description
  examples
  synonyms

後回し:
  厳密なmerge機能
  管理者承認
  統計ダッシュボード


7.3 POVページの強化

目的:
  POVを単なるタグページではなく、観点の議論ページにする。

最小構成:

  ヘッダー:
    POV名
    説明
    コメント数
    投稿数

  主張:
    A/B/C別の投稿
    一言理由
    spoiler制御

  コメント:
    最近のPOVコメント
    stance別表示

  周辺:
    似たPOV
    隣接POV


7.4 タイムラインへのPOV活動混入

目的:
  投稿だけでなく、観点の動きをユーザーへ届ける。

最小仕様:

  feed item type を増やす。

  post:
    通常投稿

  pov_activity:
    POVコメントやPOV主張の活動

  bridge_post:
    自分と遠いが共通POVを持つ投稿

  same_axis_disagreement:
    同じPOVだが異なるgrade/stanceの投稿


8. ランキングの考え方
---------------------

Daimonのランキングは、単純なsemantic similarityだけでは足りない。

理想的には、以下の要素を組み合わせる。

  score =
    semantic_similarity
    + shared_pov_weight
    + pov_activity_recency
    + pov_comment_quality
    + user_affinity_by_pov
    + disagreement_but_same_axis_bonus

8.1 semantic_similarity

投稿本文のembedding同士の近さ。

役割:
  意味的に近い投稿を探す。

限界:
  評価軸の違いまでは分からない。


8.2 shared_pov_weight

ユーザーがよく使うPOV、保存した投稿に含まれるPOV、コメントしたPOVと重なるか。

役割:
  ユーザーの感性軸に合う投稿を探す。


8.3 pov_activity_recency

最近、そのPOVでコメントや主張が増えているか。

役割:
  今まさに議論されている観点を浮上させる。

現時点では細かい統計は不要。
まずは直近のPOVコメントやPOV主張を軽くboostする程度でよい。


8.4 pov_comment_quality

POVコメントが単なる短文ではなく、理由や問いを含むか。

最初は高度な品質判定は不要。
文字数、投票、返信、保存などの単純な指標でよい。


8.5 user_affinity_by_pov

ユーザー同士が、どのPOVで近いか。

例:
  同じPOVをよく使う。
  同じPOVにコメントする。
  同じPOVで同じgradeを付ける。


8.6 disagreement_but_same_axis_bonus

最もDaimonらしい要素。

意味:
  同じPOVを見ているが、gradeやstanceが違う投稿を少し混ぜる。

目的:
  衝突ではなく、観点を共有した違いとして提示する。

例:
  あなたは「シナリオがいい」にAを付けた。
  別のユーザーは同じPOVにBを付け、「終盤は良いが中盤が弱い」と書いた。

これは、通常のSNSでは反論に見える。
しかしDaimonでは、同じ観点をより深く理解する材料になる。


9. UXの原則
-----------

9.1 統計より先に読めること

初期段階では、細かい統計機能を作り込まない。

ユーザーが最初に欲しいのは、グラフではなく「この観点で何が語られているか」を読めることである。

必要な表示:
  最近の意見
  強い主張
  違和感
  問い
  補足
  関連投稿

不要な初期表示:
  複雑な分布
  偏差値
  ランキング表
  詳細統計ダッシュボード


9.2 POVコメントは投稿コメントより上位の概念として扱う

投稿コメントは投稿に閉じる。
POVコメントは観点に蓄積される。

そのため、POVコメントは専用ページ、専用API、専用UIを持つべきである。


9.3 POVは短いが、説明可能であるべき

POV名は短くてよい。
しかし、意味が揺れるため説明が必要になる。

例:
  タイトル: シナリオがいい
  説明: 物語構成、伏線、キャラクターの変化、結末の納得感などを評価する観点。
  例: 伏線回収が自然。終盤の着地が良い。


9.4 ネタバレ制御は必須

POV主張やPOVコメントは、作品や体験の核心に触れやすい。

そのため、spoiler フラグは最初から持つべきである。

表示:
  ネタバレを隠す。
  ユーザーが明示的に開く。
  POVページでもネタバレON/OFFを切り替えられる。


9.5 ユーザーを点数ではなく感性で読む

プロフィールでは、単なる投稿数やフォロワー数よりも、よく使うPOV、よくコメントするPOV、保存したPOV傾向が重要になる。

ただし、最初から詳細統計にはしない。

まずは以下でよい。

  よく使うPOV
  最近コメントしたPOV
  よく保存するPOV


10. 参考になる研究領域
----------------------

このプロジェクトに関係する研究領域は複数ある。

10.1 Opinion Space

オンラインコメントを意見空間として可視化し、多様な視点を探索できるようにする研究。

Daimonの「感性距離」「遠いが同じ観点を持つ人」に近い。


10.2 ConsiderIt

賛否やトレードオフを構造化し、公共的な議論を支援する研究。

DaimonのPOVコメントや stance 設計に近い。


10.3 Collaborative Tagging / Folksonomy

ユーザーが自由にタグを付け、そのタグがコミュニティの共有語彙として育つ研究。

DaimonのPOVは、管理された分類ではなく、openなfolksonomyとして育つべきである。


10.4 Aspect-Based Sentiment Analysis

レビューを対象全体への評価ではなく、aspectごとの評価へ分解する研究。

Daimonの post_pov_assertions に近い。


10.5 Explainable Recommendation

推薦結果に「なぜこれが出たのか」を説明する研究。

Daimonでは match_reason, common_povs, sense_distance, is_bridge がこれに当たる。


10.6 Argument Mining / Key Point Analysis

大量の議論から主張、理由、論点を抽出・要約する研究。

POVコメントが増えた後に、「この観点では主に何が争点か」をまとめるために使える。


11. 参考になるサービス例
------------------------

ここでは、Daimonの参考になる既存サービスや設計例を整理する。

重要なのは、単にUIや機能を真似ることではない。
どのサービスが、どのように「主観」「評価」「分類」「議論」「感性」を扱っているかを見ることである。


11.1 ErogameScape - エロゲー批評空間

最も重要な参考例。

参考にする点:
  作品ページが単なるレビュー一覧ではなく、得点、コメント、属性、タグ、POV、POVコメント、音楽コメント、長文感想などの複数の視点で構成されている。
  POVが単なるタグではなく、「この観点でこの作品をどう見るか」という評価軸になっている。
  POVコメントが、普通の作品コメントとは別の層として存在している。
  A/B/Cのような強さを持つことで、「この観点にどの程度当てはまるか」を表現できる。
  古いUIでも、データ構造が深いため、ユーザーが長く読み解ける。

Daimonに取り込むべきこと:
  POVを投稿の付属タグではなく、一級のページ/導線/会話単位にする。
  投稿コメントとPOVコメントを分ける。
  POVごとの主張、理由、ネタバレ、gradeを保存する。
  作品や投稿を「総合評価」ではなく、複数の観点から読めるようにする。

Daimonでそのまま真似しないこと:
  初期段階から細かい統計表を大量に出すこと。
  データ量がない段階でランキングや分布を主役にすること。
  UIを古い情報密度のまま再現すること。

ErogameScapeから学ぶ本質:
  主観を観点に分解して蓄積すると、レビューサイトは単なる点数表ではなく、共同編集される感性データベースになる。


11.2 Rate Your Music / Sonemic

音楽作品を中心に、レーティング、レビュー、ジャンル、チャート、リスト、ユーザー評価が結びついているサービス。

参考にする点:
  作品を単純な点数だけではなく、ジャンル、descriptor、リスト、レビュー、ユーザーの好みの集合として読める。
  ユーザーが作るリストが、単なる保存ではなく「この観点で集めた作品群」になる。
  ジャンルやdescriptorが、探索の入口になる。

Daimonに取り込むべきこと:
  POVを検索語ではなく、探索軸にする。
  ユーザーが作る投稿や保存を、感性のコレクションとして読めるようにする。
  将来的には「このPOVで集めた投稿リスト」を作れるとよい。

Daimonで注意すること:
  音楽ジャンルのような比較的安定した分類と違い、DaimonのPOVはもっと揺れやすい。
  したがって、最初から厳密な分類体系を作らず、openな語彙として育てる。


11.3 Letterboxd

映画を中心に、鑑賞記録、レビュー、リスト、フォロー、いいねが組み合わさったサービス。

参考にする点:
  レビューが単なる評価ではなく、ユーザーの人格や鑑賞履歴の一部として読まれる。
  リスト機能が強く、ユーザーの観点や文脈が作品群として表れる。
  作品ページとユーザーページとリストが相互に接続している。

Daimonに取り込むべきこと:
  投稿やPOVを、ユーザーの感性履歴として読めるようにする。
  「この人はどのPOVで世界を見ているか」がプロフィールから伝わるようにする。
  保存やリストを、推薦やプロフィールに反映する。

Daimonでそのまま真似しないこと:
  作品レビュー中心の構造。
  Daimonでは対象が作品に限定されないため、中心は作品IDではなくPOVと投稿になる。


11.4 Goodreads / StoryGraph

読書記録、レビュー、棚、気分、ペース、読書傾向などを扱うサービス。

参考にする点:
  ユーザーが本を「読んだ/読みたい/積んでいる」などの状態で管理できる。
  StoryGraph系の発想では、mood、pace、character-driven などの読書体験の質が探索軸になる。
  単なるジャンルではなく、体験の質を扱える。

Daimonに取り込むべきこと:
  POVはジャンルではなく、体験の質を表せる。
  「重い」「軽い」「余韻がある」「読後感が悪いが良い」など、定量化しにくい感覚もPOVとして扱う。
  保存した投稿や反応したPOVから、その人の感性傾向をプロフィールに出せる。

Daimonで注意すること:
  読書サービスは対象が本に固定されるが、Daimonはより汎用的な感性空間を扱う。
  そのため、対象カテゴリよりもPOVを中心に置く。


11.5 MyAnimeList / AniList

アニメや漫画のデータベース、視聴状態、スコア、レビュー、リスト、ユーザー関係を扱うサービス。

参考にする点:
  ユーザーの視聴/読書履歴がプロフィールになる。
  作品ページ、レビュー、ユーザーリスト、ランキングが相互接続している。
  多数のユーザー評価が集まると、作品単位の共同知識になる。

Daimonに取り込むべきこと:
  ユーザーの投稿履歴だけではなく、POV使用履歴やPOV反応履歴をプロフィール化する。
  対象に対する評価の蓄積を、ユーザー間の発見に使う。

Daimonでそのまま真似しないこと:
  スコア中心のランキング文化。
  Daimonでは、総合点よりも観点ごとの差分を重視する。


11.6 Kialo

議論を thesis, pro, con のように構造化するサービス。

参考にする点:
  通常のコメントスレッドではなく、主張の関係を明示する。
  賛成/反対/補足のような立場が、会話の構造を作る。
  議論が深くなっても、どこに対する反応かを追いやすい。

Daimonに取り込むべきこと:
  POVコメントの stance を明示する。
  support, question, oppose, note のように、コメントの態度を分ける。
  将来的には、POVコメント同士にも「このコメントへの問い」「このコメントへの補足」を持たせられる。

Daimonで注意すること:
  Daimonは討論サービスではない。
  反論を勝敗にしない。
  目的は相手を論破することではなく、同じ観点をどう見ているかを理解すること。


11.7 Reddit / Hacker News

投稿に対してコメントが集まり、投票で可視性が決まるサービス。

参考にする点:
  軽量な投稿とコメントで会話が始まる。
  投票によって有用なコメントが上に出る。
  コミュニティごとの文脈が強い。

Daimonに取り込むべきこと:
  軽くコメントできること。
  有用なPOVコメントを上げる仕組み。
  新着、人気、議論中を分けること。

Daimonでそのまま真似しないこと:
  コメントが投稿に閉じる構造。
  Daimonでは、コメントの一部は投稿ではなくPOVに蓄積されるべきである。
  upvote/downvoteだけで会話の価値を決めすぎない。


11.8 Tumblr / Pinterest

個人の趣味、保存、再共有、タグ、ビジュアル/雰囲気による自己表現が強いサービス。

参考にする点:
  ユーザーの保存や再共有が、好みのプロフィールになる。
  タグが分類だけではなく、気分や文脈や自己表現になる。
  明示的な議論よりも、集め方そのものに感性が出る。

Daimonに取り込むべきこと:
  保存を強い感性シグナルとして扱う。
  POVを機械的カテゴリではなく、ユーザーの言葉として扱う。
  プロフィールに「この人の見方」がにじむようにする。

Daimonで注意すること:
  Daimonは画像収集サービスではない。
  保存の美学だけでなく、観点に対する言葉を蓄積する。


11.9 Stack Overflow

質問、回答、タグ、投票、信頼度が結びついたサービス。

参考にする点:
  タグがコンテンツのルーティングと専門性の表現になる。
  ユーザーの実績が、どの領域で信頼されているかを示す。
  投稿、回答、評価、タグが強く結びついている。

Daimonに取り込むべきこと:
  POVごとに「この人はこの観点でよく良いコメントをしている」が分かるようにする。
  将来的に、POVごとの貢献履歴をプロフィールに出せる。

Daimonでそのまま真似しないこと:
  正解/不正解の構造。
  DaimonのPOVは、正解を決めるためではなく、見方の差分を扱うためにある。


11.10 参考サービスから見えるDaimonの位置

Daimonは、既存サービスのどれか一つを置き換えるものではない。

近い要素を分解すると、次のようになる。

  ErogameScape:
    POVで批評を分解する。

  Rate Your Music:
    ジャンル/descriptor/リストで感性探索する。

  Letterboxd:
    レビューとリストでユーザーの鑑賞人格が出る。

  Goodreads / StoryGraph:
    体験の質や読書傾向を扱う。

  Kialo:
    議論の態度や関係を構造化する。

  Reddit / Hacker News:
    軽量な投稿とコメントで会話が起きる。

  Tumblr / Pinterest:
    保存やタグが自己表現になる。

  Stack Overflow:
    タグが専門性と貢献履歴を作る。

Daimonが目指す位置:

  ErogameScape的なPOV批評
  + Letterboxd的なユーザーの感性履歴
  + Folksonomy的なopenな語彙
  + ConsiderIt/Kialo的な構造化された立場
  + Explainable Recommendation的な「なぜ出たか」

これらを、作品レビューに限定せず、投稿SNSの速度で扱う。

つまりDaimonは、レビューサイト、SNS、タグシステム、議論支援、推薦システムの中間にある。


12. 今後のMVPロードマップ
-------------------------

Phase 1: POV主張の導入

  post_pov_assertions テーブルを作る。
  投稿作成時にPOVごとのA/B/Cと一言理由を保存する。
  投稿カードで表示する。
  POVページで一覧する。


Phase 2: POV定義の導入

  pov_definitions テーブルを作る。
  POVページで説明を表示する。
  作成者またはログインユーザーが説明を提案できるようにする。
  類義語とカテゴリは軽く持つ。


Phase 3: POVページの整理

  関連投稿
  最近のPOVコメント
  A/B/C別の主張
  似たPOV
  隣接POV
  ネタバレ制御


Phase 4: POV活動フィード

  タイムラインにPOVコメントやPOV主張の活動を混ぜる。
  同じPOVで違う見方をしている投稿を出す。
  ユーザーに「なぜこれが出たか」を説明する。


Phase 5: 軽い要約

  POVコメントが増えたら、代表的な論点をまとめる。
  最初は手動または単純な集約でよい。
  LLMやargument miningは後からでよい。


13. 現時点で作らない方がよいもの
----------------------------------

今は以下を作り込みすぎない方がよい。

  詳細な統計ページ
  POVランキング専用ダッシュボード
  ユーザー偏差値
  完全なPOV分類体系
  複雑な管理者承認フロー
  グラフ可視化
  高度なクラスタリング
  自動要約の全面導入

理由:
  まだPOV主張のデータが足りない。
  先に統計を作ると、POVが生きた会話ではなく数字になる。
  今必要なのは、観点に対して人が言葉を置けること。


14. Daimonの最小完成形
----------------------

最小完成形は、以下が自然にできる状態である。

1. ユーザーが投稿する。
2. 投稿にPOVを付ける。
3. POVごとにA/B/Cと一言理由を付ける。
4. 他のユーザーがPOVページを見る。
5. そのPOVについてコメントする。
6. 同じPOVで違う見方をしている投稿に出会う。
7. タイムラインが「近い投稿」だけでなく「同じ観点の違う意見」も提示する。
8. ユーザーは他人の感性を、投稿単位ではなく観点単位で理解できる。

この状態になれば、Daimonは単なるSNSではなくなる。

投稿を読む場所ではなく、観点を通じて他人の見方に触れる場所になる。


15. 一文でまとめる
------------------

Daimonは、主観をそのまま流すのではなく、POVという観点に分解して蓄積し、同じものを違う角度から見る人同士を接続するための、感性構造SNSである。
