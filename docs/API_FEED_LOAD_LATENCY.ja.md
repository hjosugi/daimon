# APIフィード読み込み遅延メモ

日付：2026-07-05

## 範囲

`api/internal/server/feed.loadBundle` は、タイムライン、検索、保存済み、フォロー中、キャッシュされたタイムライン、プロフィール投稿ビューの投稿カードを実現します。

## 以前

`loadBundle` はこれらの独立した読み取りを逐次的に実行していました：

1. 投稿 POV
2. 投稿メタデータ
3. いいね数
4. コメント数
5. ビューアのいいねセット
6. ビューアの保存セット
7. POVのいいね数
8. ビューアのPOVいいねセット

タイムラインのランキングは、その後バンドルの保存数を発行し、タイムラインの実現パスはQdrantのヒットが利用可能になった後に9回の逐次的なPostgreSQLラウンドトリップを行っていました。

## 変更後

バンドルローダーは、独立した読み取りを並列で実行するようになりました：

1. フェーズ1：投稿メタデータ、投稿POV、いいね数、コメント数、ビューアのいいねセット、ビューアの保存セット、タイムライン限定の保存数。
2. フェーズ2：POVのいいね数とビューアのPOVいいねセットは、フェーズ1のPOVリストが判明した後に取得。

これにより、応答内容は変更されずに済みますが、DBのクリティカルパスは8回の逐次バンドルラウンドトリップ（タイムラインの場合は9回）から、2つの依存するPostgreSQLフェーズに短縮されます。ローカルの10ms/ラウンドトリップモデルでは、これは約80〜90msのDB待ち時間が、行のデコードとレンダリングコストを除いておよそ20msに削減されることを意味します。

## 検証

ローカル検証コマンド：

- `cd api && go test ./...`
- `cd api && go vet ./...`

このリポジトリにはPostgresやQdrantのフィクスチャは含まれていないため、メモはコードパスの測定されたクエリフェーズ数を使用しており、ライブデータベースのトレースではありません。運用環境の遅延もリクエストトレーシングで確認する必要があります。
